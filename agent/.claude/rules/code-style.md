# 代码风格规范（AI-Agent）

本文从仓库实际代码中提炼，作为 Claude Code 与协作者写代码时的参照。改动遵循"与周边代码风格保持一致"的总原则。

## 1. 缩进与排版

- **缩进**：4 个空格，禁止 Tab。配置文件多行续行也使用 4 空格。
- **行宽**：无强制硬限制，长字符串与 Prompt 使用三引号多行书写。
- **空行**：
  - 顶层函数与类之间空 2 行
  - 类内方法之间空 1 行
  - 函数内逻辑分组用 1 个空行划分
- **字符串**：默认双引号,含双引号时再用单引号；f-string 优先于百分号与 format,但日志格式化保留懒求值占位符。
- **末尾空格**：不留;文件末尾保留单个换行。

## 2. 命名约定

| 元素 | 风格 |
|---|---|
| 模块文件名 | snake_case |
| 包/目录 | snake_case |
| 类 | PascalCase |
| 函数/方法 | snake_case |
| 变量 | snake_case |
| 常量 | UPPER_SNAKE_CASE |
| 模块级私有 | 下划线前缀 |
| 类内私有 | 单下划线前缀（不使用双下划线触发名称改写） |

**业务命名补充**：

- 请求/响应模型按"动作 + Request/Response"成对命名,模型字段附 description 描述用途。
- 与外部系统(前端、第三方 API)对齐的字段保持其原有命名风格(常为驼峰)，仅在内部 Python 模块用蛇形;不要为统一风格擅自改对外字段名。
- 测试类用 Test 前缀,fixture 用 snake_case。

## 3. 注释规范

### 3.1 模块 docstring

每个模块文件以三引号中文 docstring 开头,给出一句话职责;必要时附用法、环境变量、返回结构等说明。

### 3.2 函数 docstring

- 公共函数/方法必写 docstring;内部辅助函数若名字已自解释可省略。
- 用中文描述**做什么**与**关键约束**(输入格式、返回结构、副作用、外部依赖)。
- 简单函数用一行;多参数或多分支用多行。
- 不写参数列表风格(`:param:`/`:returns:`);直接用自然语言段落。

### 3.3 行内注释

- **只解释为什么,不复述做什么**。命名清楚的代码不需要旁白。
- 优先解释隐藏约束、回退理由、第三方接口怪癖、配置优先级等。
- Pydantic 字段用 description 承载文档,不用行内注释。
- 段落分隔可用横线注释作为可视区块标题。
- 不留待办占位与提交;若必须保留,写清原因与触发条件。
- **禁止生成无信息量的"AI 注释"**(等同于函数名翻译的注释,如"读取配置""返回结果""调用接口"等)。

## 4. 文件组织

### 4.1 单文件内部顺序

按从上到下:

1. 模块 docstring
2. 延迟注解的 future import(仅在确需时)
3. 标准库 import
4. 第三方 import(与上段空 1 行)
5. 项目内 import(与上段空 1 行)
6. 模块级常量
7. 模块级 logger
8. 私有辅助函数
9. 公共函数与类
10. (API 文件)路由声明

import 三段排列且每段内部按字母序;不混排不同形式的 import。

### 4.2 目录与模块边界

- 服务模块**单一职责**:新增能力优先放进既有目录的子包,不直接在仓库根加散文件。
- **禁止巨型单体文件**(项目规则明确要求)。一个文件处理一个明确职责;流水线类逻辑拆分为多个连续阶段,每阶段独立目录或文件。
- 配置文件按用途分目录管理,不同用途的配置不混放;迁移配置位置时同步更新所有读取代码。
- 包初始化文件保持轻量;仅作为包标记或显式重导出,不放业务逻辑。

### 4.3 路径处理

统一使用 pathlib,不用裸字符串拼接;项目根定位通过相对当前文件向上回溯到项目根目录。

## 5. 类型注解

- 公共函数与方法**必须**带完整类型注解(参数与返回值)。
- 使用 typing 模块的 Optional、Union、List、Dict、Tuple、Any;在切换内置泛型语法前保持一致。
- 复杂返回值优先在 docstring 给出**结构示例**,而不是写一长串嵌套类型;签名保持简洁即可。
- 默认值用 Optional 加 None;**严禁**可变默认值(空列表、空字典直接作为参数默认值);Pydantic 用 default_factory。

## 6. 日志

- 入口统一通过项目内日志模块获取 logger,**不要**自己 basicConfig 或新建 handler。
- 级别选择:
  - debug — 调试细节、入参出参摘要
  - info — 关键流程节点(开始/完成、计数)
  - warning — 可恢复异常、降级回退
  - error — 已捕获但代表故障的错误
  - exception — 在 except 块内打印含 traceback 的错误
- 结构化字段通过 extra 参数传入,便于后续聚合检索。
- 优先使用懒占位符(避免无谓字符串拼接);带变量的 debug 日志请用占位符而非 f-string。
- 异常日志带 exc_info 或直接调用 exception 方法,**不要**手动拼接 traceback。

## 7. 错误处理

### 7.1 API 层

- 业务异常映射 HTTP 状态码:
  - 入参错误 → 400
  - 外部依赖失败 → 502
  - 异步超时 → 504
  - 兜底未预期异常 → 500,且先记录含 traceback 的错误日志
- 路由内不写大段业务逻辑,组装入参后调用 service 层。

### 7.2 服务层

- 重新抛错时**保留原因链**(使用 raise from)。
- 优先**针对性 except**,只在最外层捕获兜底异常。
- 可选依赖缺失时抛运行时错误并提示安装命令或降级方案,不让进程崩溃。
- 第三方 SDK 回包结构不稳定时,写防御性分支并保留原值降级,不假设字段一定存在。

## 8. 配置与环境变量

- 所有可调参数**必须**来自配置文件或环境变量;**严禁**把密钥、URL、阈值硬编码进代码。
- 加载顺序:配置文件默认值 → 环境变量覆盖。环境变量名用全大写蛇形并加业务前缀。
- 环境变量加载只在进程入口调用一次,且必须使用项目内提供的容错加载函数(对单行解析失败仅记日志,不抛异常)。**不要**在业务模块里再次加载环境变量。
- 读取 YAML 时统一用安全加载函数,并对空文件做兜底。

## 9. 异步与并发

- 路由统一使用异步定义;IO 密集调用必须设置超时上限。
- 同步 SDK 在路由内可直接调用;若需要并发,外层封装为线程池调度,**不要**直接阻塞事件循环。
- 文件 IO 等副作用放在 service 内部完成后再返回;路由层不负责落盘细节。

## 10. 接口契约模型

- 请求模型:必填字段用必选标记,可选字段给默认值或 Optional,并附 description 描述用途。
- 响应模型:默认列表/字典用工厂函数,避免共享可变默认值。
- 字段命名遵循"对外契约保持原风格,内部模块用蛇形";嵌套结构用注释或 docstring 给出键名期望。
- 路由必须声明响应模型,并在 docstring 简短说明业务语义。

## 11. 测试约定

- 文件名以 test 前缀,与被测模块对应;类用 Test 前缀;方法名以 test 起头并描述行为。
- **mock 边界**:所有外部 API 默认 mock 掉,避免凭据缺失即失败。
- 共用资源放进 conftest 的 session-scoped fixture。
- 走真实接口的端到端测试单独命名,跑时需用详细输出模式查看中间步骤。

## 12. 提交前自检

- 单元与接口测试全部通过(被 mock 的测试不依赖凭据)。
- 服务能正常启动且健康检查接口返回成功。
- 改动若涉及架构、入参出参契约或重要决策,**同步更新**项目记忆库中的架构与进度文档。
- 不在代码中遗留调试输出与被注释掉的代码块;调试用 debug 级日志。

## 13. 反模式(明确禁止)

- 在业务模块里直接加载环境变量(应只在入口加载一次,并使用容错加载函数)。
- 自己配置日志根 handler 或用 print 做日志输出。
- 把字符串拼接的 SQL、Shell、Prompt 中的用户输入未经清洗直接传出。
- 用 assert 做运行时校验(优化模式会被剥离);改用显式条件抛异常。
- 写空的 try/except 吞错;至少要警告日志或注释解释为何静默。
- 在文件顶部使用通配 import。
- 复制粘贴一段长函数后只改一两处常量;优先抽参数或用配置驱动。
