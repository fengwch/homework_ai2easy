# 开发流程规范（AI-Agent）

本文基于项目历史(提交记录、目录结构、长期记忆库实践)总结当前的开发流程,并给出在团队扩张时需要落地的强制要求。改动遵循"约定优先、工具兜底"的原则。

## 1. 分支策略

### 1.1 主干分支

- **master** 是唯一长期分支与发布基线,所有代码最终都要回归 master。
- master 始终保持**可启动、可测试、可发布**:测试通过、健康检查 OK、无半成品代码。
- 不向 master 强制推送(force push)、不在 master 上修改历史。

### 1.2 功能分支

当多人协作或需要并行多个未完成主题时,采用短生命周期的功能分支:

- 命名格式:`<类型>/<简短主题>`,类型与提交规范的 type 对齐(feat、fix、chore、docs、refactor)。
- 单分支生命周期 ≤ 1 周;超过则拆分主题或先合并已完成部分。
- 从最新 master 切出,合并前先 rebase 或合并 master 解决冲突。
- 完成后通过合并请求(PR/MR)回归 master,**禁止**直接 push 到 master。

### 1.3 临时分支

- 实验性、不打算合并的探索分支用 `wip/` 或 `spike/` 前缀,合并前必须改名或重写为正式分支。
- 紧急修复使用 `hotfix/` 前缀,并在合并后回填到所有正在进行的功能分支。

## 2. 提交规范

项目历史已统一采用 **Conventional Commits**(`type(scope): subject`),所有新提交必须沿用。

### 2.1 格式

```
<type>(<scope>): <subject>

<body 可选,空一行后开始>

<footer 可选,如 Co-Authored-By>
```

### 2.2 type 取值

| type | 用途 |
|---|---|
| feat | 新增功能 |
| fix | 修复 Bug |
| refactor | 不改变外部行为的内部重构 |
| chore | 杂务:依赖、工具、CI、配置、清理 |
| docs | 仅文档(README、规则、记忆库等) |
| test | 仅测试改动(若与功能改动一起,优先用 feat/fix) |
| perf | 性能优化(无功能变化) |
| style | 仅格式化(空格、分号),不影响语义 |

### 2.3 scope 取值

scope 必填,使用模块或子系统的小写英文名,与目录结构对应(如 api、ocr、content_generation、voice、illustration、marketing、scripts、tools、config、env、tests、docs、project、memory-bank 等)。新增模块时同步引入新 scope,不要使用未列出的模糊 scope。

### 2.4 subject

- 使用陈述式,不超过 50 字符;首字母小写,结尾**不加句号**。
- 中英任选,但同一仓库内尽量保持团队约定的语言(项目历史中英混用,新加入者推荐统一用英文以便检索)。
- 描述**做了什么**而非过程("add async illustration endpoint" 而非 "I added")。

### 2.5 body

- 当变更原因不直观时,在 body 解释**为什么这么做**与**关键约束**。
- 与 subject 之间空一行;每行 ≤ 72 字符。
- 引用的外部资源(issue、文档链接、决策日志)放 footer。

### 2.6 原子性

- 一个提交只做一件事:**一个 feature**、**一处 bug**、**一类重构**。混合改动必须拆分。
- 自动生成产物(如缓存、构建产物、依赖锁更新)单独提交,不与功能改动混淆。
- 提交前使用补丁式暂存确认每个 hunk 都属于当前主题。

### 2.7 禁止事项

- 提交未追踪的密钥、token、个人凭据(.env、AccessKey 文件等)。
- 跳过 hook(`--no-verify`)、跳过签名;若 hook 失败,**先排查根因**再修正,不绕过。
- 默认 amend 已推送的提交;团队协作下应新建提交,避免重写公共历史。

## 3. 代码审查流程

### 3.1 触发时机

- 所有合并到 master 的改动必须经过审查(单人开发期间也建议 self-review:用 PR 视角再读一遍 diff)。
- 涉及外部接口契约、数据库结构、密钥管理、第三方服务接入、性能或安全相关改动**必须**至少一位审查者明确 approve。
- 仅文档与配置(scope=docs/chore)且不影响运行行为的改动可走快速通道,但仍需审查者点头。

### 3.2 提交者职责

PR 描述必须包含:

1. **Summary**:本 PR 解决什么问题、引入什么能力,1–3 句概括。
2. **Why now**:动机或触发事件(用户反馈、Bug、上游变更、外部依赖)。
3. **改动范围**:列出涉及模块、接口、数据结构、配置、环境变量。
4. **测试计划**:跑了哪些测试、新增了哪些测试、需要审查者验证哪些场景。
5. **风险与回滚**:潜在影响面、回滚方式。

### 3.3 审查者关注点

- **正确性**:逻辑是否符合需求;边界条件、异常路径、并发与重试是否覆盖。
- **接口契约**:对外字段命名、错误码、超时是否破坏向后兼容。
- **可观测性**:日志级别、结构化字段、错误链是否充足。
- **配置与密钥**:是否硬编码、是否走容错加载、是否在文档同步说明新增变量。
- **测试**:被改动路径是否有单元/接口测试覆盖;mock 边界是否合理。
- **简洁性**:是否引入过早抽象、是否有未使用代码、是否有"AI 注释"。
- **文档**:对外接口、运维步骤、记忆库是否同步更新。

### 3.4 反馈与回应

- 审查意见区分**Block(必须解决)**、**Suggest(建议)**、**Nit(吹毛求疵)**;Block 未解决不得合并。
- 提交者对每条意见给出回应:接受并提交 fixup、给出反对理由、或开新 issue 跟踪。
- 长讨论(>3 轮)迁移到同步会议或决策日志;不在 PR 评论里无限拉锯。

### 3.5 合并策略

- 默认使用 **Squash merge**,保留一条干净的 Conventional Commits 记录到 master。
- 多个独立主题(应当拆分却合并到同一 PR)使用 **Rebase merge** 保留每个原子提交。
- 合并后立即删除功能分支,避免分支墓地。

## 4. 测试要求

### 4.1 测试分层

| 层级 | 用途 | 何时必须存在 |
|---|---|---|
| 单元测试 | 单个函数/类的纯逻辑验证 | 所有非平凡的纯逻辑、解析、转换函数 |
| 接口测试 | 通过测试客户端调用 HTTP 路由 | 每个对外路由必须有(覆盖正常路径 + 至少一种异常路径) |
| 端到端测试 | 串联多模块的真实流程 | 关键业务链路(如:输入图片 → OCR → 内容生成 → 输出) |
| 冒烟测试 | 启动后基本可用性验证 | 每次部署前手动或自动跑 |

### 4.2 mock 与外部依赖

- 默认所有外部服务(OCR、TTS、LLM、第三方发布平台等)在测试中 mock 掉,凭据缺失也能跑。
- 涉及凭据的真实集成测试单独命名,在 CI 中按需开启,不阻塞默认测试。
- mock 的边界放在**项目自有 service 入口**,而不是 mock 第三方 SDK 内部细节,避免脆弱测试。

### 4.3 测试要求

- **新增功能**:必须配套单元/接口测试;PR 描述需说明覆盖了哪些用例。
- **修复 Bug**:先写一条能复现 Bug 的失败测试,再提交修复,确保回归可被捕获。
- **接口变更**:更新对应的 schema 测试与端到端测试;前端契约字段必须有断言。
- **测试可重复**:不依赖网络、固定时区、固定随机种子;共用资源走 fixture。

### 4.4 测试不通过时

- 提交前必须本地全量跑测试(被 mock 的部分不依赖凭据)。
- CI 失败禁止合并;不要通过禁用测试或加 skip 来"过线"。
- 偶发失败(flaky test)需立即定位:是测试本身不稳定还是被测代码有竞态。

## 5. 配置、密钥与环境

- 所有可调参数走配置文件 + 环境变量,**严禁**把密钥硬编码或提交进仓库。
- 新增环境变量同步更新示例配置文件(.env.example 或对应模板),并在 PR 描述里列出。
- 改动配置文件结构(如新增字段)需向后兼容:读取代码必须对缺失字段做兜底,**不假设**部署环境立即更新。
- 密钥泄漏时立即吊销 + 滚动 + 在决策日志记录原因与防护措施。

## 6. 长期记忆与文档同步

项目维护一个长期记忆库,作为协作者(含 AI)的项目级上下文。

- 改动若涉及**架构**、**接口契约**、**关键决策**、**外部集成**,必须同步更新记忆库中的相应文档(架构记录、进度记录、决策日志)。
- 单纯实现细节、临时调试不写进记忆库;只记可被未来读者复用的"为什么"。
- 记忆库与代码同 PR 提交,审查者验证文档与代码一致。
- 跨人协作时,先读记忆库再写代码;过期信息发现即更新或删除。

## 7. 发布与部署

### 7.1 发布前检查

- 所有测试通过;健康检查路由可访问。
- 文档同步(README、API 文档、记忆库)。
- 新增/调整的环境变量已通知运维,部署环境已就绪。
- 数据库与外部资源迁移可逆或有回滚预案。

### 7.2 发布

- 通过启动脚本或容器编排完成;**禁止**手动在生产 SSH 改代码。
- 多进程服务发布时按滚动方式,避免长耗时请求被中断。
- 发布后立即查看日志与关键指标;异常立即回滚。

### 7.3 回滚

- 默认通过部署版本回退完成;不靠"手动改回去"。
- 回滚后在决策日志或 incident 记录里写清原因与后续改进。

## 8. 提交前自检清单

每次提交前,提交者过一遍以下问题:

- [ ] 改动范围清晰,可一句话概括,提交信息符合 Conventional Commits。
- [ ] 跑通本地测试,新增/修复的代码有对应测试覆盖。
- [ ] 服务能正常启动,健康检查通过。
- [ ] 没有遗留调试输出、注释掉的代码、TODO 占位。
- [ ] 没有硬编码密钥或路径;新增配置同步示例文件。
- [ ] 文档(README、API 文档、记忆库)与代码一致。
- [ ] 改动不破坏对外契约,或已在 PR 描述声明并提供迁移说明。
